## 问题陈述

用户在聊天时经常分多条消息发送一个完整意图（习惯性按回车分段），例如：
- "帮我记一笔账"（回车）
- "午饭 35 元"（回车）
- "在公司食堂吃的"

当前系统每条消息独立触发一次 AI 推理，导致：
1. AI 只看到第一条"帮我记一笔账"就开始回复，问用户"请告诉我金额"
2. 浪费 token（每次都带完整 system prompt + 历史）
3. 用户体验割裂（收到多个不完整的回复片段）

## 用户故事

**As a** 岛主用户
**I want** 连续快速发送的多条消息被合并为一次请求
**So that** AI 能看到我的完整意图后再回复，而不是每条都触发一次推理

## 范围

### In Scope

- 前端防抖：用户发送消息后等待静默期（默认 2 秒），期间新消息合并
- 合并后的消息用换行符拼接，作为一条 user message 发送
- 防抖期间显示"正在输入..."或类似的等待提示
- 防抖时长可配置（设置页面或 config）

### Out of Scope

- 后端层面的防抖（当前只有 Web 前端，无需后端处理）
- 多平台适配（微信/Telegram 等，未来接入时再做后端防抖）
- 图片/文件消息的合并

## 验收标准

1. **AC1**: 用户在 2 秒内连续发送 3 条消息，系统只触发 1 次 AI 调用，
   AI 收到的 user message 包含全部 3 条内容（换行分隔）
2. **AC2**: 用户发送 1 条消息后超过 2 秒无新消息，正常触发 AI 调用（无延迟感）
3. **AC3**: 防抖等待期间，聊天区域显示视觉反馈（如"正在等待更多输入..."），
   让用户知道系统在等
4. **AC4**: 用户在防抖期间可以主动点击"立即发送"按钮跳过等待
5. **AC5**: 合并后的消息在对话历史中显示为独立的多条（保持原始发送结构），
   但发给 AI 时是合并的一条

## 业务价值

- 减少无效 AI 调用次数（预估减少 40% 的碎片化调用）
- 节省 token 消耗（每次调用都带 system prompt，少调一次省一次）
- AI 回复质量提升（看到完整意图后回复更准确）

## T-Shirt Size

**S** — 前端 JS 防抖逻辑 + 少量 UI 状态管理；无后端改动，无 schema 变更

## 依赖

- chat.js（前端消息发送逻辑）
- 可能需要调整 API 层的消息存储逻辑（多条消息 vs 合并后的单条）

## 技术提示（供开发参考）

参考 hermes-agent `gateway/platforms/whatsapp.py` 的实现模式：
- `_pending_text_batches` dict 按 session 聚合
- `_enqueue_text_event()` 拼接文本 + 重置 flush timer
- `_flush_text_batch()` 静默期到后统一发送
- 岛主场景在前端做即可，用 `setTimeout` + 清除机制
